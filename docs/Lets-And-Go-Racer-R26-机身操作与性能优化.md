# R26：机身操作与首轮性能优化

> 日期：2026-09-09。基础提交：`e12cb44`。设备已连接，现场没有 Joystick2 / Dual Button。
>
> 目标：使用真实车库和比赛画面完成无外设操作验证，修复明确的输入阻塞与漏操作问题，建立可重复的性能观测。外设电气和操控验收留待连接后进行。

> 尺寸勘误：设备 HAL 的真实画布为 **468×466**；早期主机截图为 466×466。历史章节的“原生 466×466”应理解为主机对照尺寸，不能据此设置设备路径的上限。第八版因此未启用半分辨率，见第 11 节。

## 1. 本轮实现

### 机身操作来源

检查或校准页按 B / 点击屏幕选择机身模式。通过专用 `GameFlow::useDeviceControls()` 转入车库，来源明确为 `device`，不伪造外设 Ready。选定后停止外设 Provider，关闭本次开启的 Grove 电源。重新进入 App 时仍支持真实外设检查/校准。

`DeviceControlSource` 分开运行 10ms GPIO 按键任务与 20ms 触屏任务。触屏内部 I²C 读取发生在共享锁外；GPIO 不依赖触屏或渲染。主线程只交换定长状态与事件，采样任务退出后才释放状态和恢复 LVGL。任务创建失败或长时间不再采样不会报告有效机身控制。

| 操作 | 机身输入 |
| --- | --- |
| 选择 / 确认 | A 下一项，B 确认；触屏两侧切换、中间确认 |
| 选车视角 | 点标题下方、车身上方区域，循环四视角 |
| 返回 | 菜单长按 A 或点顶部；选车首页返回 Launcher |
| 开赛 | 对手页选到 RACE READY 并确认，然后选择赛道、B 开始 |
| 转向 | 比赛区域按下后左右拖动，释放回中 |
| 刹车 / 增压 | 按住 A / 按住 B；长按刹车不会误暂停 |
| 暂停 / 继续 | 比赛点顶部暂停；松手后再次点击或按 B 继续 |
| 退出 | 长按 A+B 800ms，独占该次手势 |

切页会清理待消费操作，并要求释放旧手势。完整操作说明见 [使用与真机验收](Lets-And-Go-Racer-使用与真机验收.md)。

### 已确认的外设问题

- RGB 更新改为发布原子目标颜色，由原 I²C 工作任务在成功读取轴后发送。`sampleAxes()` 不再同步等待 RGB 总线写入，GPIO 快任务和 App 的快照读取不再被这条 RGB 调用链拖住。
- 总线超时后的任务节拍重新对齐，避免密集追赶过期节拍。
- `axisStatus()` 与实际轴有效性都应用连续 3 次错误阈值，避免报告 Ready 却输出无效控制。
- 后台将菜单摇杆阈值/回中转换为事件，再交给邮箱。有效短拨即使完整发生在 400ms 慢帧内，回中后也会交付一次；比赛转向仍使用最新连续量。
- 菜单切页清理邮箱并要求回中，包含两个同为横向导航的页面之间切换。邮箱合并同类方向，不承诺保存多次操作的完整次数/次序。
- Racer 恢复暂停时检查当前输入有效性；设备/外设尚未恢复时不继续比赛。外设供电失败不会继续打开 Provider。

## 2. 性能修改及边界

| 修改 | 原开销 | 当前处理 |
| --- | --- | --- |
| 渲染文件编译 | 项目使用 `CONFIG_COMPILER_OPTIMIZATION_DEBUG=y` | 只为 `garage_renderer.cpp`、`race_renderer.cpp` 追加 `-O2`；保留调试符号和断言 |
| 三角形光栅化 | 细长三角形逐行扫描整个包围盒，实体单色逐像素重复调光 | 大包围盒按行收紧扫描范围；预计算边斜率与单色调光，仍用原重心坐标规则判定像素覆盖 |
| 小三角形 | 行交点计算本身会增加开销 | 面积 ≤256 像素的包围盒保持原扫描路径 |
| 车辆遮挡 | 每个像素重复计算遮挡面朝向，调用完整线段裁剪 | 每个候选面预计算一次朝向；点遮挡专用判定；复用候选索引高位存储朝向 |
| 彩色行写入 | 材质色变化会拆成大量短绘图调用 | 车辆与赛道按连续可见区间一次提交 RGB565 行，保持像素与遮挡 |
| 近距离车辆 | 每个 112×112 小块重复变换/投影全部面，近裁剪时保守退化到全屏 | 每辆车先投影一次并缓存面包围盒，跳过与当前小块不相交的面；跨近裁剪平面仍保持原三角形裁剪 |
| 检查/赛道页面 | 即使不画车也预先建立车辆网格 | 真正画车时才访问网格缓存 |
| 静止页面 | 对手、暂停、结果及稳定后/顶视图重复整屏绘制 | 事件驱动重绘；检查/校准状态最多 250ms 刷新一次；动画页面维持原节奏 |
| 观测 | 退出时只有峰值与细节档 | 运行中每约两秒输出绘制、屏幕传输和输入处理时间及实际呈现帧数 |

保持同源实体模型、相机、材质、三档细节、赛道、物理与比赛流程。第三版主机测得渲染缓存为 `GarageSurfaceCache=591128 B`、`RaceSurfaceCache=642584 B`。比赛缓存比第二版增加 `160992 B`（约 157.2 KiB），用于最多 1548 个车面（含影子）的投影结果，由所有参赛车辆逐台复用；没有增加完整帧缓冲或深度缓冲。该空间在 Renderer 打开时分配、关闭时释放，并用编译期预算限制。输入帧由最多 20 B 调整为最多 24 B，以承载独立的菜单方向事件。

### 主机基准

运行 `bash tools/benchmark_lets_and_go.sh <输出目录>`。基准固定相机、种子与操作；每个场景预热一帧，采集 24 帧，编译使用相同 `-O2`。脚本另外包含近距离对手绕完整赛道的 High/Low 两个场景，用来覆盖普通起跑短样本未触及的卡顿路径。这里比较的是算法开销，**不包含 ESP32 编译等级改变的收益，也不代表设备 FPS**。

| 场景 | 优化前平均 ms | 首版算法平均 ms | 说明 |
| --- | ---: | ---: | --- |
| 车库 High | 2.924 | 1.925 | 约降低 34% |
| 车库 Low | 1.904 | 1.609 | 约降低 15% |
| 比赛 High | 1.141 | 1.161 | 基本持平，未证明收益 |
| 比赛 Low | 1.033 | 1.047 | 基本持平，未证明收益 |

这些是同一台开发机的一轮对照，存在负载噪声。第一版对所有三角形执行行扫描，比赛基准退化，因此调整为仅大包围盒启用，并把每行除法提前到每个三角形计算。继续优化比赛应以设备日志定位，不据此宣称达到 30 FPS。

- `/dev/cu.usbmodem83401` 的 `app-flash` 成功；只更新应用镜像，写入后 Hash 校验通过。设备串口已恢复输出。
- 用户已使用前两版完成机身模式的选车、对手、赛道和开赛流程，日志也观察到结果页、重赛与返回 Launcher。不能据此认定所有按键/触屏边界均已人工验收；Joystick2 / Dual Button 实物验收未执行。

## 4. 现场采样方法

每个页面停留至少 5 秒，取稳定窗口而非切页窗口：

1. 车库正面动画、侧面轮动、后/顶静止视角，分别记录画质档位。
2. 两条赛道预览、0 和 3 对手比赛、暂停、重赛与返回车库。
3. 同时观察 B 增压、触屏转向、点击暂停和退出；不能用静止页的零帧率判断卡死。
4. 保存 `RacerPerf` 与退出预算日志，记录固件哈希、页面、车型、赛道、对手数、音频和画质档位。

`draw_us` 是软件绘制平均耗时，`present_us` 是屏幕传输平均耗时；`fps_x10/10` 是实际呈现 FPS。`peak_us` 是窗口内绘制加传输峰值，`input_total_us` 是所有 App 更新的输入处理累计时间，不能直接当作单次输入延迟。

如果 `draw_us` 主导，继续拆赛道/车辆/HUD；如果 `present_us` 主导，查显示传输；如果输入不灵但绘制正常，查事件产生/消费与采样任务。完整外设规范见 [外设输入接入与故障排查规范](外设输入接入与故障排查规范.md)。

## 5. 前两版真机结果与第三版验证

前两版均为现场人工操作，车型、相机和比赛进度没有逐帧对齐，因此仅用于定位瓶颈，不能当作严格 A/B 百分比。

| 版本 | 车库 / 比赛测量 | 判断 |
| --- | --- | --- |
| 第一版（局部 -O2、扫描范围、输入解耦） | 车库 Low 绘制约 170–190ms；比赛 Low 约 277–308ms；传屏约 32ms | 动态车库约 5 FPS、比赛约 3 FPS，尚未达到流畅目标 |
| 第二版（RGB565 连续行、分段计时） | 车库单次：1192 面，shadow 4.2ms、raster 135.5ms、blit 10.7ms；比赛赛道约 90–120ms，车辆通常 150–180ms，部分近距离场景约 800ms | 连续行提交未解决主要瓶颈；车辆重复投影/裁剪及大范围小块遍历是后续目标 |
| 第三版（车面投影缓存与精确范围） | 用户反馈比赛仍非常卡顿；运行日志约 2.3–2.8 FPS，绘制 320–385ms，传屏约 32ms；赛道 87–146ms，车辆 188–213ms | 未解决持续卡顿，不能用主机基准收益代替真机结果 |

第三版主机基准（同脚本，24 帧）为 garage High/Low 1.708/1.572ms、race High/Low 1.153/1.033ms。主机普通比赛均值仍基本持平；不能把修复近距离重复工作直接写成整体帧率提升。

分段日志 `GarageStage` 输出 shadow/raster/blit，`RaceStage` 输出 track/cars。它们每约两秒抽取一帧，和 `RacerPerf` 的窗口均值不是同一统计口径。

证据保存在 [第一版日志](assets/r26-perf/v1.log)、[第二版分段日志](assets/r26-perf/v2-spans.log) 和 [第三版固件标识](assets/r26-perf/v3-prepared-firmware.json)。日志仅保留 Racer 性能与控制来源字段；机器上的临时文件不作为长期文档链接。

### 固定近裁剪场景对照

仅在临时副本中把 `drawRaceCar` 换回 `e12cb44` 的逐块变换实现，其余源码、编译参数、缓存尺寸和像素路径相同；对手放在玩家后方 2.2m、横向偏移 0.3m，取全赛道 24 个位置。两种可执行文件顺序交替运行三轮，避免并发争用。

| 实现 | 三轮平均耗时 ms | 三轮 P95 ms |
| --- | --- | --- |
| 逐块重复变换 | 1.465 / 1.477 / 1.466 | 2.996 / 2.868 / 2.892 |
| 缓存投影与面范围 | 0.932 / 0.950 / 0.924 | 1.279 / 1.217 / 1.205 |

主机近裁剪场景平均降低约 36%、P95 降低约 58%；普通比赛场景基本持平。这里证明该固定场景的算法收益，不能换算为设备 FPS。原始数据见 [对照 JSON](assets/r26-perf/host-nearclip-comparison.json)。

## 6. 第四版：继续降低软件绘制成本

用户反馈第三版比赛仍非常卡顿，并允许去掉远景山脉。第四版仅在比赛视图关闭山脉/地平线装饰，保留深色背景和地面色；车库赛道预览及静态结果页保持原样。

目标反汇编显示三角形边界的 `floorf/ceilf` 调用伴随多组浮点寄存器保存/恢复。用有范围保护的整数转换实现相同的像素取整，避免热循环中的库调用；超出 ±2²³ 的 float 已没有小数部分，直接保留，避免大幅离屏投影或非有限值的整数转换溢出。没有开启 `-ffast-math`。完全位于近裁剪面前的车庫四边形只投影四个顶点，两三角形共用结果。

- 渲染 ASan/UBSan 回归通过；100000 个 float 位模式与整数边界附近值对照标准 floor/ceil。
- 169 张画面中 123 张相同；46 张变化均位于 y≤162 的远景区域，下方车辆/赛道/HUD 一致。
- 增加 `TrackStage` 的 project/paint/lines 和 `CarStage` 的 prepare/raster/blit 分段，避免只依据总耗时猜测后续瓶颈。
- 第四版目标构建通过，但用户再次反馈比赛仍明显卡顿；设备主要窗口约 2.6–3.3 FPS。赛道投影约 5–10ms、填色 80–113ms；四车合计通常 130–205ms。远景删除与取整优化不足以解决持续卡顿。

第三版设备证据见 [日志](assets/r26-perf/v3-prepared.log)，第四版标识见 [固件 JSON](assets/r26-perf/v4-raster-math-firmware.json)。

## 7. 第五版：内部 RAM 工作缓冲

根据第四版 [分段日志](assets/r26-perf/v4-raster-math.log)，填色远比投影耗时，继续检查每帧的内存读写。

- 比赛 112×112 颜色/深度块优先申请内部 RAM；比赛和车库赛道各自的单行深度/颜色缓冲也优先申请内部 RAM。保留原来的嵌入缓冲作为分配失败回退，关闭 Renderer 时释放额外空间。
- 额外内部 RAM 最多 55768 B（车块 50176 B + 两组单行各 2796 B），每次申请前保留至少 32 KiB 内部空闲空间；`RacerMemory` 输出实际分配成功情况、剩余总量和最大连续块。不能把“优先申请”写成必定分配成功。
- 赛道只清理和绘制实际覆盖的 y 行，保持原 minY≤y+0.5<maxY 的规则，跳过未覆盖区域。
- 投影缓存槽切换成员仍显式开始对象生命周期，但去掉随后一定被四个顶点完整覆盖的清零写入。
- 主机嵌入缓存尺寸现在为 Garage 591144 B、Race 642600 B；以上可选内部缓冲另计，不使用第二套完整屏幕缓冲。
- 渲染 ASan/UBSan 通过，169 张画面与第四版逐字节一致；目标构建通过。新增 `PaintStage` 分别输出 clear/fill/copy。

第五版固件标识见 [JSON](assets/r26-perf/v5-internal-firmware.json)。真机效果仍须采样后确认。

## 8. 第五版实测与第六版内存拆分

第五版成功烧录并运行。设备日志明确输出 `track_rows_internal=true car_tile_internal=false free_internal=121967 largest_internal=43008`：赛道行缓冲成功启用，车辆缓冲因最大连续块不足 50176 B 而回退，并非设备没有更新。原始证据见 [第五版日志](assets/r26-perf/v5-internal.log)。

普通比赛采样窗口约 3.4–4.0 FPS，部分复杂视角仍约 3.2 FPS。赛道填色普通段约 42–46ms，较第四版约 80–113ms 的观察值下降；但手工比赛进度没有对齐，不作为严格 A/B 比例。赛道覆盖接近全屏时填色仍约 75–79ms。`PaintStage` 显示普通段清零约 9–10ms、深度填色约 16–18ms、写回约 15–16ms，仍有明显优化余地。

第六版把车辆 50176 B 的连续申请改为颜色、深度分别申请 25088 B，各自有原存储回退；额外内存总量不变。`car_planes_internal` 输出 0/1/2，分别表示没有、一块或两块成功进入内部 RAM。嵌入缓存尺寸变为 Garage 591152 B、Race 642608 B。

目标构建与渲染 ASan/UBSan 均通过，169 张画面与第五版逐字节一致。第六版标识见 [固件 JSON](assets/r26-perf/v6-split-firmware.json)，实际分配与帧率待下一轮设备记录确认。

## 9. 第六版实测与第七版共享顶点缓存

第六版确认 `track_rows_internal=true car_planes_internal=2`，剩余内部 RAM 70763 B、最大连续块 31744 B；车辆两块缓冲都已成功启用。用户反馈有所改善但仍不流畅，日志主要窗口约 3.4–4.0 FPS。见 [第六版日志](assets/r26-perf/v6-split.log)。

第七版保持原生 466×466 画面：

1. 相邻车面按原始位置和轮组建立共享顶点索引，每个共享顶点每帧只变换/投影一次；每个车面的 UV、颜色、光照和绘制次序继续独立保存。跨近裁剪平面沿用原三角形裁剪。八款车 Low 原始角点数为 2956–3860，唯一顶点为 934–1378。
2. 反汇编发现深度清零被编译为 `s8i` 逐字节循环。对两个 Racer 渲染文件添加 `-fno-builtin-memset` 并显式调用 memset，已确认调用 ROM 的 `memset`，消除反复大块清零的逐字节展开。

### 可复用的性能排查顺序

1. 记录实际画布尺寸、实际渲染模式、内部 RAM 分配结果、车辆数量和赛道/车型标识，再比较帧率。请求开关打开、构建成功、烧录成功分别都不等于优化路径已生效。

4. 先保留画面一致性；必要的分辨率取舍只作用于场景，HUD 和输入坐标保持原生。记录新增缓冲、分配失败回退和重入释放。
5. 主机验证数学/遮挡/生命周期，真机验证字节序、内存分配、实际帧率和主观操作。单车、四车分别测，固定配置重跑；未对齐的手工数据只作为观察区间。

## 15. 第十一版：比赛低分辨率材质与小地图静态缓存

用户提出降低比赛贴图质量，以及停止、删除或局部刷新小地图。代码核实后：当前车型同源且已有 Low/Medium 几何档位，场景也已半分辨率；但非纯色涂装仍在每个可见像素执行完整程序纹样，包括字体、分支、fmod 和渐变。小地图仅缓存了投影几何，每帧仍画 96 段道路、接触阴影和边线，不能称作已缓存底图。

第十一版把比赛专用优化拆为两项：

1. `RacePaintAtlas` 将原程序材质以 32×32 RGB565 烘焙，含底色和面片光照，最近邻查表；透视 UV、近裁剪、遮挡、几何与轮动保持原通路。车库保持原完整材质。最多 64 种材质变体，131460 B 固定表，缓存缺失或容量不足回退原材质；仅参赛车型/档位变化时重建，日志输出 texture_side、entries 和 fallback_panels。
2. 小地图底图烘焙为 87×87 Sprite（15138 B 像素），换赛道时重建。每帧在场景放大之后透明贴回底图，再绘制当前车辆标记，保留导航作用；圆外透明区域不会覆盖比赛背景。帧内局部贴回不等于屏幕局部传输：HAL 仍整帧传屏，不能用此修改声称消除约 32ms 的 present。

`HudStage` 新增 map_us（含车辆标记）、total_us 和 map_cached，首次可以单独观察小地图成本。旧版缺少该分段，不预先量化删除/缓存小地图能节省多少时间。画面质感取舍为细字、灯纹、网纹变粗或减少，主要辨识色块仍保留。

完整 ASan/UBSan 与目标构建通过；182 张原有画面完全一致，新增 24 张八车型生产对照，检查了两赛道、单人/四车、画质变化、近距离对手、缓存失效和重入。已人工打开查看八车对照，自动证据检查通过。详细材质卡、两轮自审、预算和证据见 [比赛材质缓存卡](Lets-And-Go-Racer-R26-比赛材质缓存卡.md)。

[固件标识](assets/r26-perf/v11-material-firmware.json)。已 app-flash 成功，Hash 校验通过并 RTS 重启。实际纹理缓存命中、小地图缓存启用、颜色及 FPS 待当前设备下一轮验证，不提前声明收益。


## 16. 第十一版实测与第十二版玩家画质优先

第十一版设备确认 35 种烘焙材质、`fallback_panels=0`、`map_cached=true`，内部 RAM 剩余 70079 B、最大连续块 31744 B。14 个 RACING 窗口范围为 4.5–8.6 FPS、中位数 5.7 FPS；本轮玩家换为 car=0，不能与第十版 car=1 的中位数作严格 A/B。用户反馈超越全部对手后明显变快，同时指出玩家车马赛克感过强。

本轮性能假设是减少每帧一辆对手的模拟与绘制成本；不是依靠进一步降低玩家画质。真机验证需确认 `cars=3`、`wireframe=false`、相同玩家/赛道下的帧率区间与主观观感。当前同时恢复实心路面并减少参赛车数，下一局不能将变化全部归因为其中单项；如仍不可接受，可在本版直接选一名对手做双车对照，无需再次修改固件。

## 22. 第十五版三车与双车实测对照

用户完成两种场景后，日志确认两局均使用第十五版、Sonic（car=1）、SkyLoop（track_id=0）、234×233 实心场景（`wireframe=false`）和原生玩家绘制。第一局三车，CarStage 覆盖 0/1/2，即 Magnum、Sonic、Tridagger；第二局双车，覆盖 0/1，即只移除 Tridagger，保留 Magnum 对手。两局均进入 RESULTS，所采日志无 panic / abort / watchdog。第二局重入后内存缓存再次成功分配，材质缓存分别 19 项和 11 项，均无 fallback。

判断：减少参赛车数确有可见的性能收益，但双车仍只有约 7 FPS，尚不能宣称已达到流畅目标或用户已接受。单纯继续减少对手的空间有限；双车剩余的主要绘制成本是玩家约 38ms、赛道约 16ms、场景放大约 19.5ms，以及传屏约 32.2ms。若继续优化，应检查这些阶段的处理效率和复制成本，保持当前赛车画质；小地图约 1.4ms，仍不是优先项。
