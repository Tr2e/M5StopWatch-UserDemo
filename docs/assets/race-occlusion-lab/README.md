# 比赛车辆合成：按扫描行筛选遮挡候选

2026-09-10，ESP32-S3 StopWatch。承接玩家降采样／材质缓存未采纳的实验，本轮保持车型、贴图、玩家原生分辨率、小场景分辨率和相机不变。

## 改动及正确性约束

原路径先筛选与 112×112 车辆 tile 相交的赛道面，再由每个有车身像素的位置遍历这些候选。新路径在每个扫描行开始时，进一步排除点数小于 3、或 Y 包围范围不包含该行像素中心的面；其余索引按原顺序保存，逐像素仍使用原来的包围框、深度、绕序和凸多边形测试。

行坐标仍为 `(_y+y+.5f)*occlusionScale`，与原逐像素坐标一致。筛选采用严格小于／大于，保留原有包含边界的规则；没有对深度平面重排浮点运算，没有修改采样或放宽精度。筛选条件全部属于旧像素循环中已有的排除条件，所以不会增加或减少符合遮挡条件的面。

行列表最大 624 个 uint16_t 索引，占 1248 B。初版把它放在任务栈，固定序列最小栈余量降到 1148 B，未直接交付该版本。修订版使用 `RenderScratch` 在比赛打开时尝试分配内部 RAM，遵循已有的 32KiB 预留策略；失败自动沿用旧候选遍历，不新增栈数组或全屏缓冲。比赛关闭时随 surface cache 释放。车库不申请这块内存。

`RaceRenderStages` 增加同帧所有已提交车辆的 prepare／raster／blit 累加值及候选行数量，正常限频 `RaceStage` 日志也记录这些字段。候选行数量是“列表长度 × 行”的总和，**不是实际逐像素判断次数**：车身空白像素会跳过，命中遮挡也会提前终止。它用于解释工作集变化，不直接当作耗时下降比例。

## 受控方法

同一固件、同一 renderer、同一缓存分配，按 `mode=0`（原遍历）和 `mode=1`（行筛选）切换。8 车型 × 2 赛道 × 25 个位置，每组第一帧预热，384 个计时快照／模式；每个快照轮换执行先后顺序。共 800 次渲染，400 组整屏 CRC 比较。

使用正常 garage 内存分配及比赛 234×233 小场景、468×466 原生画布，玩家 Medium、两名对手 Minimal；固定速度状态 12m/s、种子 42。两名对手分别在 +0.5m / -0.25m、车道 ±0.55m，每四帧把第二名改到 -2.2m，覆盖近裁剪情形。环道均匀采样经过桥区；这不替代人工连续驾驶、并排超车及全部遮挡组合的验收。

绘制和真实同步全屏呈现分别计时；CRC、逐帧输出和快照调整在计时外。正常限频日志仍可能出现在绘制区间，两种模式共同承受。记录每一帧耗时，P95 使用最近秩，可计算本轮全部 384 帧的分位数，不平均不同车型的 P95。

实验没有并行运行真人输入、比赛音频或十分钟稳定性测试；耗时不能当作端到端输入延迟。各轮快照数量和设备状态可能不同，只在本轮配对模式间计算收益。

## 证据与复现

- `baseline/`：本轮前的 renderer、raster、主机测试、主入口和 CMake 文件。
- `stack-prototype/`：第一次完整实验源码、日志、哈希和统计；这个栈上版本已被替代。
- `experimental/`：将行列表移到可选内部 RAM 的实验源码和测试，临时入口 `occlusion_device_benchmark.cpp`。
- 将 renderer／raster 文件复制回同名原路径，测试文件对应 `tools/lets_and_go_renderer_test.cpp`；把临时入口置于 renderer 目录，在 HAL 与 Wifi 初始化后调用 `occlusionDeviceBenchmark()`，为该源设置 `-O2;-fno-builtin-memset`，重新配置构建。设备实验结束后必须移除入口并重新配置正常固件。
- `python3 docs/assets/race-occlusion-lab/analyze.py` 从最终 `ab-device.log` 生成 `frames.csv` 和 `summary.json`。
- 所有写入均先核验 StopWatch 83401 / 303A:1001 / 44:1B:F6:C1:8A:00，只写 0x20000 应用分区；PaperColor 83301 不参与。

主机检查包含 240 组随机遮挡面 × 2 种坐标比例、624 候选满容量及边界相邻浮点值、未分配行列表时的回退、八车型实际比赛新旧路径对照。既有 356 张生产场景逐字节比较另行保留。

## 最终结果与采纳

内部 RAM 修订版，同一固件中每种模式 384 个计时帧：

| 指标 | 原遍历 | 按行筛选 |
| --- | ---: | ---: |
| 整帧平均（绘制＋呈现） | 158.876ms | 156.067ms |
| 绘制平均 | 127.393ms | 124.584ms |
| 呈现平均 | 31.484ms | 31.483ms |
| 车辆几何准备平均 | 22.961ms | 22.964ms |
| 车辆光栅平均 | 46.007ms | 46.013ms |
| 车辆合成平均 | 14.559ms | 11.540ms |
| 整帧 P95 | 188.980ms | 185.101ms |
| 整帧最大值 | 215.223ms | 206.461ms |

平均整帧少 2.810ms（1.77%），合成少 3.019ms（20.74%）。15/16 个车型／赛道组合整帧更快；car=1 / track=1 组平均反而慢 0.588ms，不能宣称所有场景都改善。其他阶段与限频输出的波动使整帧节省不恰好等于合成节省；P95 和最大值仅为本轮观察值，不作为长期最差帧保证。

候选面与扫描行组合总数从 1,487,136 降至 453,431，减少 69.51%，但仍需光栅、像素遮挡和送显，因此不把这个比例写成帧率提升。

400 组真机 CRC 全部一致。完整 ASan/UBSan 游戏、外设控制、Vector Run、Launcher、生产 renderer 测试通过，356 张生产画面与前版逐字节一致。原生画质保持的收益足够覆盖 1248 B 列表的代价，**正式启用按行筛选，并保留未分配时的旧路径回退及测试开关**。

实测行列表分配成功，深度／颜色两块 tile 和赛道行缓冲仍在内部 RAM。修订版实验开局内部 RAM 可用 96239 B、PSRAM 可用 5559444 B，末尾分别为 96231 B / 5559444 B；这只覆盖一次固定序列，不构成长时间无泄漏证明。车库／比赛 surface 对象各增加一个可选 scratch 指针；车库不分配行列表。

修订版任务最小剩余栈仍为 1132 B，未观察到整体高水位改善；栈上初版为 1148 B。这些值包含初始化、绘制与日志等调用链，不能把局部数组移出栈直接换算成任务高水位改善。最终 `blit` 的编译栈帧为 0x5b0（1456 B），仍包含原有 tile 候选数组，见 `blit-stack-frame.txt`；正常 App 调用链与长时间操纵的栈余量尚未单独验证。

两轮实验各 400 组 CRC 零差异。初版整帧 159.094→156.044ms、16/16 组更快，只作为方向复核；正式数值使用修订版结果，不跨两个固件拼接统计。
