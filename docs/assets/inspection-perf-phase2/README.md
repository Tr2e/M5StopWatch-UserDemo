# VIEW CAR 后续优化证据

最终保留固定 80%（282×230）交互绘制与释放后原生高清，High 模型和程序涂装不变。

## 最终实现

1. 欣赏模式对相邻面共享的几何顶点建立索引，每帧只变换、取景和投影一次。面自身 UV、颜色、光照和原始绘制顺序独立保留；近裁剪退回原路径。保留原 352×288 颜色／深度缓冲。
2. 连续欣赏同一车型时只向屏幕传输车辆区域（468×466 实机上为 x=40、y=70、388×322），包括全部阴影和边缘。进入／离开欣赏页、切换车型和重新打开 App 仍完整刷新。根据最近实际呈现的页面判定，不依赖当次输入循环的旧页面。
3. HAL 使用目标显示的裁剪功能保留源 sprite 的行跨度与色彩转换，传输后恢复原裁剪状态；其他页面／App 继续使用原全屏接口。没有增加 framebuffer。

主机上 GarageSurfaceCache 从 591168 B 增至 722256 B（增加约 128 KiB 的几何索引／工作空间）；目标构建与测试通过。索引建立使用临时 32 KiB 哈希表，申请失败则采用不合并顶点的正确退路。

## 验证

`final-tests.log`：完整 ASan/UBSan，包含游戏、输入、Vector Run、Launcher 和生产 renderer。640 个欣赏视角对照原取景结果；8 车型 × 80 视角 × 80%／100% 验证变化像素全部位于刷新区域内。332 张前版生产图逐字节一致。呈现策略覆盖进入、持续操作、切换车型、离开、重入和打开重置。

`device-ab/phase2_*` 是临时真机测试源，已从正常构建移除。Reference renderer 复现前版完整缓冲与逐面即时着色，采用相同的模型、涂装、取景、缩放、阴影和 UI。两个 cpp 与生产 renderer 均采用 `-O2 -fno-builtin-memset`。测试在 HAL 初始化后、App 安装前执行，完成后恢复 main.cpp、CMakeLists.txt 并移除临时源。

同一 ESP32-S3 进程交替运行两条绘制路径，8 车型 × 80%／100% × 13 视角，剔除首帧，其余每组 12 帧记录整页绘制均值／最大值，并比较完整 RGB565 framebuffer CRC。全屏与局部传输也交替先后，单独计时。分配比赛缓冲模拟主要内存占用，但没有运行真人触摸、外设采样或比赛音频，因此不是实操 FPS／输入延迟验收。

## 已放弃的试验

`ab-*` 为条带与共享顶点版本，`deferred-*` 为延后着色版本，`ordered-*` 为近面优先并保留等深度序号的版本。这些方案通过像素检查，但真机收益小或部分车型退化，均未保留。早期 host stable 日志也只属于这些探索，不代表最终版本。最终数据使用 `refresh-*`，最终正常固件另见 `firmware.json`。

所有串口操作均核验 StopWatch `/dev/cu.usbmodem83401`、USB `303A:1001`、序列号 `44:1B:F6:C1:8A:00`，仅写应用分区 `0x20000`。PaperColor `83301` 未打开。

最终设备结果：80% 绘制＋传输 175.43 → 158.10ms（减少 9.88%），100% 为 209.65 → 192.43ms（减少 8.22%）；全屏约 31.1ms，局部约 18.3ms。208 组 CRC 相同，原始数据见 `device-summary.csv` 和 `device-ab/refresh-device.log`。正常固件烧录并启动 Launcher，版本核验见 `final-device.log`。
