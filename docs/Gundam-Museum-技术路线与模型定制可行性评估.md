# 高达博物馆：技术路线与模型定制可行性评估

评估日期：2026-09-13。对象：当前 StopWatch 仓库的 Mini 4WD / VIEW CAR 技术路线。基础提交 `6b9512f`，工作区另有首页美术等未提交改动。本次只做源码审查、现有证据核对和主机模型统计；没有制作高达成品、修改游戏、构建新固件或测量高达真机帧率。

**结论：值得做单机展台式原型。低多边形、高辨识度的高达收藏馆具备可行性；达到什么还原度和旋转流畅度，要由第一台模型的生产渲染和真机测试决定。** 当前路线最适合图鉴选藏品、单台实时旋转、自动巡展、预设站姿、配色及装备组合。把所有藏品同时放进可自由行走的实时 3D 大厅，会显著扩大渲染和内容预算。

## 1. 当前技术实际上是什么

官方硬件资料为 ESP32-S3R8、双核最高 240MHz、16MB Flash、8MB PSRAM、466×466 圆形 AMOLED。当前 `sdkconfig` 配置 240MHz CPU、80MHz 八线 PSRAM；HAL 实际画布/面板配置存在 468×466 与 466×466 的区别，UI 应按生产坐标及圆形可视安全区验证。

来源：[M5Stack StopWatch 官方资料](https://docs.m5stack.com/zh_CN/core/StopWatch)、`sdkconfig`、`main/hal/hal_display.cpp`。

现有链路是：

`型号目录 → C++ 独立建模函数 → CarPanel 面片 → 顶点去重/相机变换 → 自动取景 → 软件三角形光栅 → 深度测试与涂装 → RGB565 画布 → 局部送显`

- `model/car_display_mesh.cpp` 与 `car_mesh_builder.h` 生成实体几何，车库和比赛共用来源。
- `CarPanel` 存四个位置、颜色、部件标签、有限 UV 范围、程序涂装 ID、明暗和轮动标记。一个 panel 按两组三角形处理，部分 panel 用重复顶点表示单三角形。
- `car_surface_raster.h` 使用 16 位逆深度缓冲、近裁剪和透视校正 UV。可以处理机体、盾牌、手臂和背包的前后遮挡。
- `car_paint.h` 主要是 UV 程序色块/纹样，VIEW CAR 没有通用外部图片材质或 PBR 管线。现有明暗主要在建模阶段写入，不是随展厅灯光变化的完整动态光照。
- `CarInspectionController` 支持触屏/摇杆旋转、复位和限位；`InspectionAutoController` 已有自动巡展。
- 绘制仅缓存当前车型。角度、页面、材质/质量等改变时才需要重绘；博物馆可以沿用按需刷新。

关键源码：`main/apps/app_lets_and_go_racer/` 下的 `model/car_display_mesh.h`、`view/car_surface_raster.h`、`view/garage_inspection_cache.h`、`view/garage_car_transform.h`、`controller/car_inspection_controller.h`。

## 2. 已有证据与性能边界

2026-09-10 的 `docs/assets/inspection-compact/summary.json` 记录了八车型、固定姿态序列的真机均值：

- 拖动档：内部 65% 绘制、85% 显示，绘制 106.16ms，送显 18.50ms，合计 **124.66ms**。
- 原生档：100% 绘制/显示，绘制 170.06ms，送显 18.43ms，合计 **188.49ms**。
- 用 `1000 / 平均合计毫秒` 换算，分别约 **8.0 / 5.3 帧每秒**。这是该基准的吞吐量等价值，不是本次测出的高达帧率，也不是平均瞬时 FPS 或真人输入延迟。

因此不能承诺直接换成高达就有 15–30 FPS。减少比赛逻辑也不意味着欣赏页会成倍加速，因为该基准本来就是单车展示。

当前源码已比这份历史记录继续演进：拖动仍为 65% 绘制/85% 显示；松手等待 **100ms**，用 **520ms** 平滑恢复显示大小，最后补原生帧；自动巡展为 **90% 绘制、100% 显示**，一周 **20 秒**。历史文档中的 150/300ms 两档恢复不能当作当前实现。没有发现当前 AUTO 90% 路径对应的新真机基准。

本次用生产建模函数重新统计八台 High 模型：1,171–1,565 panels；排除退化面的有效三角形约 2,078–2,794；去重顶点 1,366–2,095；全部无容量溢出。详见配套 `Gundam-Museum-model-probe.txt`。**现有 2,048 的硬上限是 panels，不是三角形数。**

主机 `sizeof(CarPanel)=60 B`，`sizeof(CarDisplayMesh)=122,896 B`，`sizeof(GarageSurfaceCache)=763,184 B`，`sizeof(GarageRenderer)=7,128 B`。前两项说明数据布局，后两项为主机 ABI 的对象大小，不代表设备实时内存峰值。当前 surface 的 768,000 B 静态预算已经接近用满，旧文档 591KB/722KB 数字不应直接作为现状。

八车约 88%–96% 的 panel 已是 Solid。因此“高达主要用纯色”有利于简化制作，但不能据此推断巨大加速；屏幕覆盖面积、遮挡重绘、三角形形状和余下纹样成本仍要测量。

## 3. 最适合的产品形态

建议把“博物馆”做成展柜与藏品组织方式：

`展馆入口 → 系列/展柜图鉴 → 单台展台 → 旋转、细节、装备与档案 → 保存陈列方案`

第一阶段可包含：单台实时旋转、自动巡展、正/背/侧视、头胸细节镜头、机体档案、收藏状态、收藏夹、一个标准站姿和一个装备姿势。展柜总览使用由同源模型生成的缩略图，切入单台时启用实时 3D。

收藏循环可以围绕“解锁藏品/资料 → 选择涂装装备 → 摆放展台 → 完成系列展柜”。先验证展示吸引力，再决定解锁任务和经济系统。

能力判断：

- **适合作为第一版**：单机展示、图鉴、收藏存档、分区换色、底座铭牌、武器/盾牌开关。
- **可行但需要新增实现**：预设关节姿势、头部/背包细节镜头、少量附加部件、局部灯色效果。
- **先单独验证**：大翼展/大量浮游炮、多机同屏、自由关节编辑、透明光束叠层。
- **不宜作为当前路线首版承诺**：高精 CAD 等级近看、完整 PBR 反射、复杂骨骼连续战斗、变形机构动画、大型自由漫游展厅。

## 4. 复用边界与必须补的技术

推荐新增独立博物馆 App，把显示算法、输入生命周期和证据工具作为复用基础。不要把高达硬塞进 `CarSpec`，更不要继承赛车速度/对手掩码作为藏品结构。

### 可以复用

RGB565 画布、深度/裁剪/光栅算法、局部送显模式、当前模型缓存、触控所有权与输入故障处理、自动巡展的控制思路、真实 renderer 出图与两轮模型审查。

共享算法应维护单一来源。需要通用化时使用薄适配层/材质采样接口，并为赛车保留原适配器和像素回归，不复制出两份长期分叉的光栅器。

### 必须新增或适配

1. **机体定义和部件树。** 建议以 `ExhibitSpec` 保存稳定 ID、版本、模型构建入口、配色、装备、预设相机和姿势；`PartNode` 保存父部件、局部位置/旋转、关节轴心及材质区。名称仅是设计建议，尚未实现。
2. **人形相机。** `GarageCarTransform` 会根据赛车宽长比缩放 x；它必须改为通用单位比例。旋转中心放在机体合适高度，地面另行定位，俯仰范围按人形观看需求设置。
3. **稳定取景。** 当前 fit 随角度调整大小，宽背包/盾牌可能让主体明显忽大忽小。为每台机体和装备组预计算全周安全包络，巡展保持尺度；细节模式单独设置观察点和裁剪，不能继续让全身自动 fit 抵消放大操作。
4. **装甲部件配方。** 增加闭合斜切装甲、楔形胸块、头盔/脸罩、裙甲、关节筒、脚部和背包接口。现有 `box` 没有底面，`tube` 无端盖，`duct` 开口固定朝 +z；直接套用会在背视/俯视露出破面。
5. **姿势变换。** 当前 `wheel` 只是轮动标签，`parent` 是保留的旧附件字段；没有可直接使用的通用骨骼系统。第一版使用刚体父子变换，在换姿势/装备时重建一次展品网格和索引，再用现有路径旋转展示。以后连续关节动画要把 part ID 纳入顶点去重，避免同位置不同部件被错误绑定。
6. **机甲材质。** 首版用分面明暗、RGB565 色块和少量 UV 标识；眼睛可用不受普通暗化的亮色近似，但实际自发光/光晕需要新增。装甲缝靠几何分区或面内纹样，避免大量共面贴片产生闪烁。
7. **展品存档。** 存机体 ID、解锁状态、配色 ID、装备 ID、姿势 ID 和展柜位置，加版本迁移；不存完整网格。赛车当前 `uint8_t` 对手掩码不能作为超过八件藏品的结构。

## 5. 模型定制的三条制作路线

### A. 现有 C++ 参数化方法：最短验证路径

每台机体有独立结构函数，关节/装甲/喷口用公共零件配方，配置控制颜色、武器和姿势。优势是与现有生产引擎直接衔接、资源可控，尤其适合硬表面机械。成本在于比例和细节需要逐轮出图调整；不能指望改同一个通用人形的颜色就代表不同机体。

第一台适合按此方法完成，以便先证明当前显示质量和性能能承载目标审美。大量机体持续使用纯手写坐标，内容维护会成为主要成本。

### B. Blender 可编辑模型 → 离线转换：后续批量制作路线

流程为 `.blend 源文件 → 分部件低模/确定姿势/材质区 → 导出或直接读取 Blender 数据 → PC 转换器 → 设备面片或专用索引网格`。

Blender 用于直观调整剪影和装甲结构；离线工具负责单位轴向、变换、面数、材质映射、关节标签和边界校验。设备只读整理后的简单资源，不在运行时承担完整 Blender/glTF 材质解析。

**仓库目前没有这条通用导入链路，不能把“Blender 能导出 GLB”当作设备已能读取 GLB。**

- 现格式只有每个 panel 的矩形 UV 范围，不支持任意网格的独立顶点 UV。首个转换器应限定纯色材质/简单程序材质，并清楚拒绝不支持的输入。
- 一个独立三角形用退化四边形表示时会占一个 panel。2,500 个导入三角形会超过当前 2,048-panel 容量，即使几何复杂度与现有车接近。应尽量保留合法平面凸四边形；或另行设计紧凑索引三角形格式及适配路径。不能单纯扩大数组。
- 需要拒绝/处理非有限坐标、退化面、错误绕序、非平面/凹四边形及越界索引；转换后用生产渲染确认颜色、正反面和开口。
- 导出后重新统计顶点：UV 接缝/硬边会使导出顶点增加；材质节点也不保证能等价转换。

参考：[Blender 官方 glTF 导出说明](https://docs.blender.org/manual/en/4.0/addons/import_export/scene_gltf2.html)。本评估采用其格式限制原则，不依赖特定新版界面操作。

### C. 现成高模或 AI 3D → 人工重拓扑：作为辅助输入

可以用于观察形体或制作草模，但不应作为首版自动生产管线。复杂高模往往包含大量在小屏不可见的内构和细分；直接减面可能破坏脸部、天线、装甲边界及部件间隙。需要人工保留辨识点、重做部件关系和材质，并转换成 A/B 的设备资产。

Blender Decimate 可以降低面数，但减面工具不会替你决定哪些机体特征必须保留。参考：[Blender 官方 Decimate 文档](https://docs.blender.org/manual/en/5.0/modeling/modifiers/generate/decimate.html)。

## 6. 一台模型的具体制作闭环

沿用 `skills/reference-model-workshop/`：参考 → 结构/材质卡 → 几何 → 涂装 → CR1 结构审查 → CR2 生产显示审查 → 真机验收。

1. **锁定版本。** 例如选择 RX-78-2，也要确定采用哪个设定/套件版本、正常比例还是 SD、携带哪些装备。正背侧与三分之四视角保持同版本，记录不可见结构的推断。
2. **先画灰模。** 拆头、胸、腰、骨盆、裙甲、上/下臂、手、上/下腿、脚、背包、武器和盾牌。先在最终屏幕尺度验证头身比、肩宽、腰宽、腿长和站姿。
3. **保护辨识点。** 天线、脸罩、胸部进气口、裙甲、脚尖和背包必须有合适轮廓。双腿间、手臂与躯干间、背包与身体间保留真实空隙。小屏全身站姿看不清眼睛时，优先提供头胸镜头，而非无限增加面数。
4. **增加折面和厚度。** 装甲不是一堆等边方块；用少量有方向的斜切面表现肩、胸、小腿与脚。关节圆周段数按屏幕大小配置，阴暗内构只保留实际能看到的部分。
5. **配色与定制。** 每块装甲关联语义材质区，玩家换色改调色板；武器/盾牌通过挂点切换；姿势改关节变换。颜色、装备、姿势变化均更新缓存键。第一版限定组合，不做任意部件自由拼装。
6. **CR1。** 正背侧、两侧斜视、俯视检查剪影、比例、关节连接、封口和穿插；低档仍保留识别特征。
7. **CR2。** 用实际 C++ 渲染器检查圆屏裁切、持盾遮脸、背包遮挡、天线闪烁、材质方向、切姿势后的取景、拖动与原生恢复。保存全身和头胸细节的生产原帧。
8. **设备验收。** 连续拖动、巡展、换装、退出重入；记录帧时间分布、输入样本年龄和可测的呈现延迟、最小空闲内部 RAM/PSRAM。首台通过后再做下一台。

参数化定制容易扩展配色和装备；新的机体结构仍然是新的内容制作任务。收藏数量本身不是最难的部分，逐台保持还原度才是。

## 7. 建议预算与存储策略

**以下是原型起点，不是已验证的高达容量。** 首台 High 可先设 1,000–1,500 panels，含常用装备并保留余量；有效三角形另记，尽量控制在现有车约 2,000–3,000 的量级。天线、脸部和主要剪影不因降档消失。首轮只保留需要的档位，避免一开始为比赛式三档增加工作。

沿用 352×288 raster 时，颜色+深度基础数组为 `352×288×4=405,504 B`。如果改成 300×336 竖向窗口，相同计算为 403,200 B，像素预算接近，但 raster 模板、缩放、取景、UI、刷新区和安全区都需相应适配并真机重测。高达的竖向构图值得试，但不是仅修改两个数字。

运行时只展开当前藏品网格；其他机体保留源配方或紧凑资源。50 台按每台 1,200 panels、每 panel 60 B 直接打包原始面片，光几何约 **3.6MB（十进制）**，不含缩略图、材质和程序。这说明大量藏品应考虑量化顶点/索引/部件实例及按需加载，不能常驻全部展开网格。程序生成模型的 Flash 成本要看编译产物，不能用 RAM 面片大小代替。

`partitions.csv` 中每个 OTA app 为 `0x4f0000`（5,177,344 B），另有 4MiB storage；16MB Flash 不等于全部都能给新 App。2026-09-10 历史镜像余量约 0.22MiB；本地 2026-09-12 `.bin` 为 3,822,768 B，按分区算余量约 1.29MiB，但未重建/核对该产物与当前工作区一致，**不能作为新功能已可装入的证明**。接入时需重新构建确认 Flash、数据分区实际占用和 OTA 兼容性。

## 8. 分阶段决策

**阶段一：一台技术样机。** 建议基础 RX-78-2 作为待确认选题，包含站姿、盾/枪、手动旋转、自动巡展和头胸镜头。先锁版本，再制作结构卡。交付真实渲染图、计数、内存和设备数据。

样机门槛：

- 用户认可原尺寸全身和细节图的辨识度；各方向无明显破面、穿插及裁切。
- 先争取连续旋转的处理时间不劣于历史缩小交互档约 125ms，并单独报告 P95/最慢帧及输入延迟；这只是比较基线，不代表 8 FPS 已满足体验。
- 12–15 FPS 可作为提升目标，需要总帧时间约 83–67ms，经真机达到后才能承诺。
- 换装/换姿势后状态和取景稳定，松手恢复正确，重复进出无持续内存损失。

**阶段二：三台内容样机。** 加入一台曲面比例更高的机体和一台宽背包/翼展机体，验证部件配方、内容差异、包络和复杂装备预算，再决定是否投入 Blender 转换器。

**阶段三：收藏游戏。** 添加系列展柜、解锁、档案和保存陈列。选 5–8 台形成一版完整内容，再用真实每台制作成本决定后续规模。

主要未知项是首台视觉接受度、复杂装备真机帧时间、当前完整固件资源余量、具体系列/版本与批量制作效率。技术路线不需要推倒重来，但通用人形模型层、相机取景和内容制作管线是实质性新增工作。
