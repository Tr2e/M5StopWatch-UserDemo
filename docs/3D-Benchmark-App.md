# 3D Benchmark App

`3D Benchmark` 是一个独立的四段式全帧真机性能演示，不再借用 Gundam Museum 的交互循环。FPS 取预热后相邻 framebuffer 提交完成时刻的平均间隔，包含场景绘制、提交调用、帧间 1 ms 调度延时和普通循环开销；异步面板 DMA 的完整物理传输可与下一帧重叠，不能把该数值解读成“每帧都等待面板扫描完成”。测试过程中不显示 HUD，完整演示结束后只绘制一次静态结果页，后续按键等待不持续重绘或提交 framebuffer。

## 测试路线

1. **Cube Pair（3.4 秒）**：显示两个六面异色立方体，分别使用不同配色、大小、远近、旋转轴和透视姿态。
2. **Rigid Assembly（3.4 秒）**：只显示 4 个 64 共享顶点、48 四边形、8 刚性骨骼的 rigid chain；四条链分别使用独立调色板、大小、深度和空间姿态。
3. **Mixed Load（3.4 秒）**：组合 4 个第一阶段的异色立方体与 2 个第二阶段的刚性链，继续保持独立配色、尺度、深度和姿态。
4. **RX-78 Final（6.8 秒）**：释放程序场景工作区，再打开生产 Gundam Museum 渲染器，以所选内部采样、Z-buffer 和双核路径显示 RX-78 单体转台；角速度仍按 10 秒一周计算，因此本阶段约旋转 `0.68` 周，不强制补齐一整周；空间线框和导航控件关闭，背景为 RGB565 `0x0000`。

前三段沿用《ESP32-S3 高性能 3D 渲染框架提炼与模型接入规范》已实现的 S0/S1 公共路径：模型只在场景工作区建立一次，之后以不可变 `ModelAsset` 常驻；两套立方体和四套刚性链的配色都在资产构建、校验和 seal 之前写入，seal 后不再修改。资产显式携带共享索引、三角/四边形拓扑、法线、anchor、bounds、groundY、确定性顺序、S0 纯色材质与内存报告；刚性链另带 8 个刚性分件。帧循环只更新轻量 `ModelInstance.world` 并引用预分配 `BoneTransform`，静态与刚性实例统一经 `renderSceneCachedIndexed` 进入 solid fast path，不进行逐帧建模、堆分配或任务栈大对象构造。刚性路径会为每个实例缓存 64 个已变换、已投影共享顶点，并将 8 组 `world × pose[rigidPart]` 仿射矩阵各合成一次。固定 pitch/roll 的正余弦只在工作区初始化时计算，每帧只计算各实例变化的 yaw，不为固定姿态重复调用三角函数。

100% 模式使用 424×424 内部颜色/深度平面，按 occupancy 只合成有覆盖的原生像素；60% 模式使用 254×254 内部平面，通过同一 occupancy 驱动的稀疏最近邻放大到中央 424×424 输出。两种模式都使用稀疏深度清理，并在原生 RGB565 framebuffer guard 成立时直接写入 framebuffer。纯黑背景和配色变化不改变资产拓扑。

阶段 1–3 的光栅器在图元 setup 时以 O(提交图元数) 顺手维护保守覆盖 bounds，不在帧尾扫描整张 depth/occupancy；App 为两个异步 framebuffer 分别保存上一帧 bounds，每次只清理“当前 framebuffer 上次覆盖 ∪ 本帧覆盖”并提交该矩形。RX-78 的纯黑单体转台也使用双 framebuffer 独立历史脏区，但当前 bounds 直接搭载在本来就要执行的并行 occupancy 合成上：上下行带各自产生局部 bounds，join 后取并集，不增加第二次 occupancy 扫描，也避免两个光栅核心竞争共享 bounds。两个 framebuffer 各自第一次使用时仍完整清黑，且发生在 300 ms 预热期，避免未初始化像素和双缓冲残影。任一 native layout guard 失败时回退完整显示 API；带全屏旋转空间线框的 Gundam Museum 仍保持全屏背景/提交策略。

四段在一次测试中统一使用当前选择的 100% 或 60% 内部采样，RX-78 是最终阶段。阶段资源构建完成后才设置起始时间，随后 300 ms 为预热，避免把分配/建模时间吃掉预热窗口或把冷首帧纳入结果。结束页不再计算综合评分，主要显示每段的 `TOTAL TRI`、平均 `DRAW TRI` 和平均 FPS，并以小号次级信息补充 `TOTAL QUAD / DRAW QUAD`。TRI 仍是主负载口径，四边形在 TRI 中按两个 triangle 计数；QUAD 用于表示保留原生四边形拓扑、可利用 solid-quad 快速路径的数量，不代替像素成本指标。前三段的 TOTAL/DRAW 都由公共 Soft3D 前端在已解析 topology 上顺手累计，在单面背面、近裁剪可见性和完整屏外检查前后分别记录，不额外遍历资产、不由结果页硬编码或反推；被 Z-buffer 遮挡但已提交的图元仍计入 DRAW，与 RX-78 的 submitted 统计保持同一语义。

### 结果口径

屏幕 FPS 为 `1 / 平均帧时`，用于阶段成果展示，不是 P95 认证。前三段只有 3.4 秒且扣除 300 ms 预热，不报告 P95、最大帧、温升、内存水位或长时间稳定性。任何 30/24/20/15 FPS 产品等级仍必须使用独立的连续帧真机流程签署，不能从本结果页直接推导。

统计器不允许反过来改变被测工作量。FPS 每帧只读取一次 `esp_timer_get_time()`；阶段边界日志和结果页均在采样窗口外。公共资产在既有 topology 分支上累计 TRI/QUAD；RX-78 这类历史 panel 资产仅在模型重建时判定一次拓扑并缓存 TOTAL 与逐面 quad 位图，帧循环提交面只读取 1 bit，禁止重新比较三个顶点坐标或扫描整张网格。

2026-09-23 在同一台 StopWatch 上对“完整统计”与“编译移除 TRI/QUAD 统计”各自动运行 3 轮 100%→60%。优化后的最大差异是 60% Mixed Load 的 `+0.394% / -0.126 FPS`；RX-78 为 100% `+0.003% / -0.000 FPS`、60% `+0.088% / -0.014 FPS`，因此产品保留统计。计时器 20,000 次设备微基准为 `0.949 µs/call`；相对本次最短约 29.3 ms 帧间隔约 `0.003%`。这是当前固件和编译布局的 A/B，不应外推成所有平台常数。

## 操作

- A：在运行中或结果页重新开始完整测试，保留当前渲染比例。
- B：在 100% 与 60% 内部渲染之间切换，并立即重新开始完整测试，避免结果混用两种分辨率。
- 同时长按 A + B：退出到 Launcher。

## 生命周期与内存

程序资产与 RX-78 不同时驻留。前三段结束后先释放两种立方体配色资产、四个刚性链资产和 424×424 光栅工作区，再创建 MuseumRenderer；结果页前再次释放 RX-78 工作区。内部 RAM 先申请每像素访问的 occupancy，再申请实例/pose/cache hot state，并一次性日志记录两者是否成功；失败时使用常驻回退存储。Wi-Fi 在测试打开时按已有 Museum 策略暂停，退出后恢复。Gundam Museum 自身保持正常交互，不自动运行旧的临时批处理基准。

## RX-78 高性能经验审计

阶段 1–3 已逐项复核 RX-78 中可通用的优化，不能只凭 fast-path 开关存在就视为接入：

| 项目 | 阶段 1–3 状态 |
| --- | --- |
| 不可变资产、共享索引、四边形拓扑、S0 纯色 | 已命中 |
| 静态/刚性唯一顶点 camera transform 缓存 | 已命中 |
| 唯一顶点投影缓存 | 已命中；静态立方体和刚性链均走相同 indexed scratch |
| 刚性 `world × pose[rigidPart]` 预合成 | 已命中；`Bone.parent` 不由 runtime 求值 |
| 背面、近裁剪、屏外提交前剔除 | 已命中，并输出真实 TOTAL/DRAW |
| compact solid、span、trusted depth、solid quad | 已命中；不再只是打开未被调用路径的开关 |
| 稀疏深度清理与 span clear | 已命中 |
| occupancy 记录策略 | 四个阶段的 100%/60% 都在光栅期记录，以支持稀疏合成与历史覆盖清理；只有带全屏动态背景的 Museum 原生路径保留 deferred 记录 |
| 稀疏原生合成 / 稀疏放大 | 100% 只复制 occupied 原生像素；60% 只放大 occupied source pixel |
| native RGB565、脏区清黑、异步局部提交 | guard 全部成立时命中；双 framebuffer 各自保存历史脏区，首次完整初始化，失败正确回退显示 API |
| occupancy、实例、pose、变换/投影 scratch 内部 RAM 优先 | occupancy 优先级高于 hot state；成功项可从 `3DBenchMemory` 日志核对，失败回退常驻工作区 |
| 固定姿态与结果页 | pitch/roll 三角函数移出帧循环；结果页只绘制/提交一次 |
| 生产 FPS 去除逐像素诊断计数 | 已命中；前三段使用非 measured raster |
| 生命周期、Wi-Fi、工作区互斥释放 | 已命中 |

双核行带、12 B indexed command stream 和 split color/depth 没有无条件复制：当前前三段使用 common 单核即时提交路径，提交图元显著低于 RX-78，F4 同机标定中 crate 与单 rigid chain 也选择 single。当前 Demo 的分段真机数据证明，真正不适合复制的是 RX-78 的密集全屏清理、全目标扫描和全屏提交，而不是全部共享优化。相反，span 稀疏深度清理、solid-quad、共享顶点投影缓存和刚性矩阵预合成在反向 A/B 中仍有净收益，继续保留。

### 稀疏场景专项真机结果（2026-09-23）

同一台 StopWatch、统计开启、自动入口、相同资产与镜头。基线为全屏清黑且 100% 扫描完整 424×424 合成；最终版为光栅期 occupancy、稀疏原生/缩放合成、双 framebuffer 独立历史脏区和 O(1) bounds 读取。数值为 `1 / mean(frame interval)`：

| 模式 | 阶段 | 基线 FPS | 最终 FPS | 提升 |
| --- | --- | ---: | ---: | ---: |
| 100% | Cube Pair | 20.8 | 44.7 | +114.9% |
| 100% | Rigid Assembly | 16.7 | 28.7 | +71.9% |
| 100% | Mixed Load | 19.1 | 36.5 | +91.1% |
| 60% | Cube Pair | 33.9 | 73.0 | +115.3% |
| 60% | Rigid Assembly | 29.5 | 51.9 | +75.9% |
| 60% | Mixed Load | 32.0 | 60.7 | +89.7% |

基线三段每帧全屏清黑均约 `17.6 ms`；最终 100% 分别降至 `1.65 / 2.78 / 2.71 ms`，60% 为 `1.69 / 2.85 / 2.83 ms`。100% 的完整目标合成由约 `16.22 / 15.16 / 15.57 ms` 降至 `6.56 / 5.16 / 5.71 ms`。第一版脏区实现仍在帧尾扫描 occupancy 求 bounds；改为 setup 阶段顺手维护保守 bounds 后，100% 又由 `41.6 / 27.5 / 34.5` 提至 `44.7 / 28.7 / 36.5 FPS`，证明“小数据结构的全量扫描”在短帧中也需计入。

反向 A/B 也保留负结果：关闭 span 稀疏深度清理后，100% 三段比最终配置低 `7.2% / 2.8% / 3.0%`，60% 低 `1.9% / 1.3% / 2.1%`；关闭 solid-quad 后，100% 低 `4.3% / 3.1% / 3.6%`，60% 低 `1.5% / 3.5% / 3.6%`。因此不能按“场景简单”批量关闭 RX-78 验证过的内核优化，必须按固定管理成本、像素覆盖、数据重放量和真机端到端结果逐项选路。

### RX-78 纯黑转台专项结果（2026-09-23）

旧路径即此前定位出的“每帧大面积清黑 + 100% 完整扫描 424×424 合成”。最终路径为双 framebuffer 独立历史脏区、光栅期 occupancy、原生/缩放稀疏合成，并将并行合成行带的实际写入 bounds 顺手并入提交范围。最近邻映射按当前 source/output 尺寸缓存生成；不能把 Museum 65% 的 `276×276→424×424` 表复用于 Benchmark 60% 的 `254×254` 或 100% 的 `424×424`。稀疏合成的行缓存移入渲染器持久工作区，避免大数组叠加到 `main`/worker 深调用栈。

同一设备最终候选连续三轮结果如下；阶段计时存在双核重叠，不能相加：

| 模式 | 旧帧间隔 / FPS | 最终帧间隔 / FPS | 清黑 | 合成 | FPS 提升 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 100% | 112.335 ms / 8.9 | 90.720 ms / 11.0 | 12.952→4.389 ms | 22.443→10.203 ms | +23.8% |
| 60% | 64.438 ms / 15.5 | 51.498 ms / 19.4 | 11.337→4.248 ms | 5.223→5.429 ms | +25.1% |

60% 合成数值小幅增加不是重新引入完整扫描：旧表错误地固定按 276 source 生成，新路径按真实 254 source 采样并顺手输出 bounds；正确性工作量略增，但清理、PSRAM 争用和完整关键路径显著下降。100% 的 occupancy 写入也不是免费的，必须看端到端结果；本次帧间隔降低 `19.2%`，因此保留。将带 bounds 的 helper 抽到阶段 1–3 通用热循环曾使其下降约 5–10%，最终已拆为“无 bounds 通用版本”和“RX 持久 scratch + bounds 版本”；最终三段恢复到 100% `44.7 / 28.7 / 36.5 FPS`、60% `72.9 / 51.9 / 60.7 FPS`。

另有两个已识别但未冒然接入的候选：公共即时前端会在遍历图元时缓存首次出现的投影顶点，不像 RX-78 两阶段前端那样先完成全部面分类，因此可能为随后被剔除的面做少量无效投影；增加预分类也会带来第二次遍历和命令存储，需真机 A/B。同时，两套 cube/四套 chain 为了独立调色板复制了几何资产；后续可评估“共享几何 + 实例材质表”，但它主要影响常驻内存/缓存，不应在没有数据时宣称会直接提升 FPS。

### RX-78 投影缓存稳定化（2026-09-24）

后续三轮自动重建暴露出旧的 32,088 B 连续片内投影缓存依赖偶然堆形态：稳定最大连续块只有 31,744 B，缓存失配时 60% 由约 19.3 降到 18.0 FPS。最终保留完全相同的 32-bit 浮点值，将 `x/y/z` 改为三个约 10.7 KiB 的 SoA 块并采用 all-or-nothing 回退；行带选择只读取 y。60% 三轮稳定为 `52.031 / 52.001 / 52.049 ms`（`19.2 FPS`），100% 为 `86.601 / 86.628 / 86.613 ms`（`11.5 FPS`）；六次 RX 会话缓存全部命中，阶段 1–3 无有意义回归。相对缓存稳定失配的 60% 基线，帧时降低约 `6.18%`。主机 60/65/90/100 共 1,408 组 framebuffer 逐像素一致，ASan/UBSan 通过；证据见 [`assets/rx78-60-percent-e3/README.md`](assets/rx78-60-percent-e3/README.md)。该结果优先解决性能可重复性，尚未达到计划中的 22 FPS。

随后按 60% 的真实 `254×254` 尺寸把片内 occupancy 从 22.5 KiB 缩到约 8.1 KiB，完整 424 位图仍作为 PSRAM 回退。释放的预算使 25.3 KiB 索引命令块和直接上下带流稳定命中；三轮 60% 进一步降到 `51.157 / 51.149 / 51.141 ms`（`19.5 FPS`），100% 保持约 `86.61 ms / 11.5 FPS`。相对稳定失配基线累计降低 `7.77%`，阶段 1–3 不受影响；证据见 [`assets/rx78-60-percent-e4/README.md`](assets/rx78-60-percent-e4/README.md)。

E5 在 prepared sparse solid-quad 光栅中按扫描行缓存当前 occupancy byte，把连续像素及两个子三角形的 bit 合并写回；不改变颜色、深度、覆盖或提交顺序。三轮 60% 为 `50.947 / 50.933 / 50.965 ms`（均值 `19.63 FPS`），100% 为 `85.654 / 85.693 / 85.670 ms`（均值 `11.67 FPS`），主机 1,408 组 framebuffer 逐像素一致。该特化增加约 1.5 KiB 片内代码，60% 最终 internal free 约 23.1 KiB，因此只作为高覆盖且必须记录 occupancy 的实测选路，不升级为所有图元的默认成本；证据见 [`assets/rx78-60-percent-e5/README.md`](assets/rx78-60-percent-e5/README.md)。

E6 复用直接命令路径中闲置的片内 band scratch，单次扫描生成保持原顺序的背/正面索引流，替代两次全资产重扫。60% 三轮为 `50.832 / 50.830 / 50.860 ms`（均值 `19.67 FPS`），panel prepare 平均减少约 `0.080 ms`；100% 与 E5 等价，未新增常驻内存或固件体积。证据见 [`assets/rx78-60-percent-e6/README.md`](assets/rx78-60-percent-e6/README.md)。
