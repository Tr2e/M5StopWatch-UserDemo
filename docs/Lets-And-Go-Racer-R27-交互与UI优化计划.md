# R27：交互与 UI 优化计划

状态：进行中，启动入口、开赛准备、比赛 HUD、倒计时与结算首轮已实现。用户已明确将交互与 UI 提升为最高优先级；R26 作为已验证的代码基线固定。

## 当前基线

- 比赛使用红、蓝、白实心赛道，最多三辆车（玩家加两名对手），支持单人和双车。
- 保留当前赛车画质、原生玩家绘制、对手材质缓存及小地图缓存。
- 支持机身按钮/触屏和外设两种明确选择的输入模式，保留独立采样、失联中性控制和暂停/退出。
- 第十五版同玩家、同赛道实测：三车 FPS 中位数 6.6，双车 7.4；未达到流畅目标。完整主机测试与 ESP32 构建通过，外设电气实操仍待完成。
- 性能阶段与证据见 [R26 记录](Lets-And-Go-Racer-R26-机身操作与性能优化.md)。后续以此为回归对照。

## P0：优先完成的交互与界面工作

1. **打通开赛主流程。** 从选择操作模式、车型、对手到赛道和开赛，明确当前步骤、已选状态和下一步操作。对手页清楚显示人数、选择上限与开赛入口；选满、取消和替换都有可理解的反馈。
2. **统一触屏与按钮语义。** 确认、返回、暂停、继续、重试保持一致；用明确的点击区域和选中反馈降低对说明文字的依赖。核对短按/长按、按住、松开、拖动和切页后的事件归属，避免误触和旧手势穿透。
3. **改善比赛 HUD 与圆屏布局。** 优先保证玩家车辆与前方道路可见；重新安排名次、圈数、速度、增压和操作提示的层级、字号、对比度与安全边距。检查当前底部信息卡对车辆的遮挡。
4. **完善暂停和结算。** 清楚区分主动暂停与输入失联，突出可执行的恢复动作；重试、回车库、退出有清晰选中态和结果反馈。

以上是基于现有界面的首轮待验证重点，具体布局在实现前以当前生产画面和真机操作核对；不把待办写成已完成。

## 实施与验收

- 按“流程与状态反馈 → 比赛 HUD → 暂停/结算”逐步实现，每批提供可查看的画面和设备版本。
- 优先使用已有控件和绘制能力；关注可读性、触达和操作反馈，不以新增装饰动画增加慢帧成本。
- 两种输入模式分别验证：无外设机身操作可立即测试，Joystick2 / Dual Button 接上电气后再完成实际操作验收。
- 验证选择、取消、满员替换、开赛、拖动转向、刹车/增压、暂停/继续、结算、重试与退出重入；慢帧下仍保持采样独立和失联保护。

## 比赛音乐开销对照

按用户要求，RACING 使用 `MusicScene::Off`，跳过背景音乐合成，保留起跑、增压、碰撞、圈数等提示音。车库和结算音乐仍保留，HAL 音频流及采样率不变；这次测的是背景音乐开销，并非关闭整个音频系统。新增 `RacerAudio` 启动日志记录 `race_music=false`、音效设置和音频流是否打开。

音频 ASan/UBSan 测试通过，覆盖关闭音乐时的 14 种提示音、采样率、分块一致性和暂停恢复；ESP32 构建通过。4926720 B 固件已 app-flash、Hash 校验及 RTS 重启，`/dev/cu.usbmodem83401` 串口已连接，日志 `/tmp/racer-device-no-race-music.log`。帧率尚待用户运行，不能提前判断提升。

对照配置沿用 R26 v15 的 Sonic / SkyLoop：三车（Magnum、Tridagger 对手）原中位数 6.6 FPS，双车（Magnum 对手）7.4 FPS。原始记录中音效设置为 true、代码启用比赛音乐；手动路线、AI 位置与取样区间未同步，后续比较需说明这一限制。[本版固件](assets/r27-audio/no-race-music-firmware.json) · [音频测试](assets/r27-audio/audio-test.log)。

### 首局实测：整体帧率提高，尚不能归因为音乐

用户完成一局后，串口确认 `race_music=false sfx_enabled=true stream_open=true`，Sonic（player_car=1）、SkyLoop（track_id=0）、cars=3、234×233 实心场景和原生玩家绘制，并进入 RESULTS。稀疏 CarStage 记录只覆盖车型 1/2，因此不能仅靠此日志完整确认两名对手身份。日志未发现 panic / abort / watchdog。

| 指标 | R26 v15 三车、有音乐 | 本局三车、无比赛音乐 |
| --- | --- | --- |
| RACING 汇总窗口 | 14 | 12 |
| FPS 窗口中位数 | 6.60 | 7.35 |
| FPS 范围 | 6.2–6.9 | 5.6–8.6 |
| draw 窗口中位数 | 115.414ms | 99.700ms |
| present 窗口中位数 | 32.176ms | 32.111ms |
| 最大 peak_us | 173.665ms | 218.662ms |
| 玩家绘制采样中位数 | 35.767ms | 35.407ms |
| 放大复制采样中位数 | 19.507ms | 19.524ms |

关键混杂因素：旧局 13 个 RaceStage 样本中，12 次 submitted=3、1 次=2；本局 11 个样本中，6 次 submitted=1 且 opponents_us=0，只有 5 次 submitted=3。此处 submitted 是实际提交绘制数，不等于参赛人数，也不保证有可见像素。本局前四个 RACING 窗口为 6.1/6.5/6.6/6.3 FPS，附近阶段记录仍提交三车；随后出现 5.6 FPS 窗口，附近一次对手绘制耗时达 91.527ms。后半程连续仅提交玩家的采样附近，窗口达到 8.0–8.6 FPS。阶段是独立稀疏采样，不能将其当作对应窗口每一帧的完整状态或精确因果分解。

因此，本局整体中位数上升约 11.4%，但绘制负载明显不同，不能把差值当作关闭音乐的收益。现有证据更支持“少画对手时帧率上升”；尚未证明背景音乐是主要瓶颈，最慢帧也没有改善。保持当前比赛无音乐版本，未再次改动或烧录固件。若需定量分离音频开销，应在可重复的相同车辆位置/相机状态下比较，或添加合成耗时和锁等待测量。

统计口径保持 R26：包含全部 RACING 汇总窗口（首个可能含倒计时），阶段样本只取首末 RACING 时间戳之间，不混入结算；不将不同阶段中位数相加为逐帧分解。[本局原始日志](assets/r27-audio/no-race-music-device.log) · [逐窗口与分段统计](assets/r27-audio/no-race-music-observed-comparison.json)。

## 第五批：边缘装饰清理与点击命中修复

用户认可第四批 UI 基本正常，指出左右红蓝露出含义不清，以及经常点不准；进一步确认最常发生在 NEXT / START RACE。左右露出来自 `home_theme::backdrop` 的边缘装饰矩形，并非按钮，本批已删除。

代码检查发现以下明确问题并修正：

1. NEXT / START RACE 原共用 156×38 区域，边缘外无容差，首次按下坐标决定整次动作。本批扩大可见按钮至 184×44，命中另留 4px 余量。菜单使用松手确认和最后有效接触坐标；允许初次接触在 16px 内微调落入控件，进入某控件后滑出会取消，不能拖到另一按钮执行。
2. 选车页仍使用整片上方/左右/中间作为隐藏热区。本批改为明确的视角标签、左右圆形箭头、SELECT 和返回；对手及赛道页同样只命中可见导航控件。命中分两遍：先匹配可见矩形，再考虑余量，避免邻居的扩展范围抢占按钮。
3. 新页面状态在画面送屏之前已更新，释放采样可能提前重新启用下一页输入。本批增加 `presentScreen` 门禁；页面第一次送屏完成后，再通过释放重新启用按键/触屏，避免按旧画面点击却操作了新页面。
4. HAL 之前将读失败表现为 num=0，且只看 finger_num、忽略驱动已解析的 Up 状态。本批增加 `TouchPoint.valid`，num 尊重 CST820 `isPressed()`；Racer 失败时取消触摸手势、不刷新成功采样时间，不将错误转换成释放点击。GPIO 采样与点击日志仍在不同执行位置，日志不持有输入快照锁。

新增 `RacerTouch` 记录页面、按下坐标、最后有效接触坐标（日志字段 up）、目标和 accepted。显示配置确有 offset_x=6，但它是显示存储地址配置，尚无实测证据证明触屏也需要减 6。本批未盲加坐标偏移/缩放；系统性偏移需下一轮点主按钮的设备日志确认。

验证：完整 ASan/UBSan 回归通过，随后针对可见区域优先匹配和标签微调的输入与生产 Renderer 复验通过，ESP32 最终构建通过。新增测试覆盖主按钮/结果按钮每个可见像素的目标一致性、边缘余量、首点微调、拖到邻居取消、读取失败不能点击、显示/释放门禁、慢帧 GPIO、实时转向和结算目标。279 张图中 100 张因装饰删除和控件改版改变、179 张不变；比赛 HUD/赛道/车辆保持上一版。物理触屏校准及所有其他 App 的真实触屏操作尚未进行，不能把本轮主机通过写成硬件定位完成。
