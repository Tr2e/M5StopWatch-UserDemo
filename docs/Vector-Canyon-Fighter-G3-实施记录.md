# Vector Canyon Fighter：G3 实施记录

## 切片 G3.1：静态可运行场景

**范围**：应用壳、低预算峡谷线框与第三人称战机静态构图。此切片刻意不接入飞行物理、IMU、Joystick2 或 Dual Button。

### 交付物

- `AppVectorCanyonFighter`：可从应用列表打开和返回主页的独立应用。
- `vector_canyon_renderer`：以现有 `HAL` canvas 绘制黑底峡谷。
- 8 个深度环的线框峡谷：符合 Low 图形预算的起步配置。
- 原创、后方追视的线框战机：位于画面下部中间，宽约 62 px，明显小于圆屏直径的 18%。
- 克制 HUD：仅显示名称、速度、巡航与 IMU 就绪状态；未加入扫描线、随机标签或装饰性赛博元素。

### 设计校准审查

| 检查项 | 结论 | 证据 |
| --- | --- | --- |
| 视角是第三人称而非第一人称 | 通过 | 战机始终画在下部前景，峡谷向远处收束。 |
| 战机比例不过大 | 通过 | 机体宽约 62 px；466 px 圆屏中约占 13%。 |
| 峡谷承担穿梭感主体 | 通过 | 两侧岩壁、地面与深度连接线共同构成可读空间，战机未遮挡主体。 |
| 视觉遵守线框复古未来感 | 通过 | 黑底、低亮度绿青峡谷、浅色机体；无照片式渲染或随机装饰。 |
| 尚未偏离输入抽象目标 | 通过 | 此切片不读取任何控制器，避免在 `FlightInput` 设计冻结前写死输入方案。 |
| 实时预算有起点 | 通过 | 33 ms 帧间隔（约 30 FPS）和 8 个深度环，符合 G2 的 Low 起步预算。 |

### 构建验证

- 新增的两个 C++ 源文件已进入 ESP-IDF 的编译数据库并生成对象文件。
- `make -C build -j14` 成功生成 `build/StopWatch-UserDemo.bin`。
- 应用二进制为 `0x460680`，最小 app 分区 `0x4f0000`，余量 `0x8f980`（约 11%）。
- 已执行 `git diff --check`，无空白错误。

### 待验证与下一切片

- **真机视觉门禁仍待执行**：刷入 StopWatch 后确认圆屏裁切、线条亮度、文字边距和战机实际占比；未完成前不把 G3 整体标记为完成。
- G3.2 将引入固定步长的 `FlightInput` / `FlightModel` 与可循环的地形推进，但仍只使用 IMU 与表体按键平替输入。

## 切片 G3.2：确定性推进与地形流

**范围**：以固定步长推进飞行距离，使用固定容量、固定种子的峡谷切片构成可循环的空间流；此切片仍不读取 IMU、GPIO 或 I2C。

### 交付物

- `FlightInput`：冻结的规范化输入数据契约。
- `FlightModel`：以 1/60 秒固定步长平滑更新速度、横移、高度、滚转、俯仰与推进状态。
- `TerrainStream`：8 个固定容量切片；按固定种子和段编号生成，近裁切面后复用到远端，无逐帧动态堆分配。
- Renderer 改为只读 `FlightState` 和 `TerrainStream`，以简化透视投影生成动态峡谷，并让战机姿态与速度 HUD 读取飞行状态。

### 设计校准审查

| 检查项 | 结论 | 证据 |
| --- | --- | --- |
| 地形是持续推进的空间而非静态背景 | 通过 | 每个模拟步以 `forwardDistance` 推进；近端切片循环到远端。 |
| 可重现性 | 通过 | 固定种子 `0xC4A71001` 和段编号决定切片参数；不依赖帧号或运行时随机数。 |
| 模型与硬件隔离 | 通过 | `FlightModel`、`TerrainStream` 无 HAL/GPIO/I2C/LVGL 依赖。 |
| 渲染器只读场景数据 | 通过 | Renderer 接收 `const FlightState&` 与 `const TerrainStream&`，不修改模型。 |
| 低预算仍受控 | 通过 | 固定 8 切片，单帧无容器增长；保留小比例战机与必要 HUD。 |
| 输入功能是否被伪装为完成 | 通过 | 应用目前只注入中性巡航输入；IMU/按键明确留给 G3.3。 |

### 构建验证与发现

- 初次定向编译发现 `TerrainStream` 漏引入 `<cstddef>`，导致 `size_t` 未定义；已修正，未提交带错误版本。
- 修正后，`flight_model.cpp`、`terrain_stream.cpp`、`vector_canyon_renderer.cpp` 与应用入口均完成目标编译，并成功重新链接 `esp-idf/main/libmain.a`。
- `git diff --check` 通过。

### 待验证与下一切片

- 真机仍需检查：圆周内裁切、实际帧时间、近景切片是否过度跨越屏幕边缘，以及长时间运行时的内存稳定性。
- G3.3 只实现 `ImuButtonInputProvider`：会话内中性校准、死区与平滑；A/B 调节速度和触发短时推进，A+B 仍返回 Launcher。

## 切片 G3.3：IMU + 表身按键输入

**范围**：实现临时控制器，不触碰最终 Joystick2 / Dual Button 的 I2C/GPIO 接线与驱动。

### 交付物

- `InputProvider` 抽象接口；`ImuButtonInputProvider` 是当前唯一实现。
- 打开应用后约 650 ms 采样会话内中性姿态；校准前输出 `valid=false`，右下角显示 `IMU CAL`。
- 校准后：加速度差经死区与一阶平滑映射到 `steer` / `pitch`；A/B 短按下调/上调目标速度；B 长按只产生一个 `boostPressed` 边沿。
- A+B 返回 Launcher 仍由既有 `KeyManager` 优先处理；游戏不篡改该系统约定。

### 设计校准审查

| 检查项 | 结论 | 证据 |
| --- | --- | --- |
| 临时输入与最终输入可替换 | 通过 | App 持有 `InputProvider`，模型只接收 `FlightInput`。 |
| 输入失效不会沿用极端姿态 | 通过 | 校准前 `valid=false`，`FlightModel` 转为中性轴和安全巡航油门。 |
| 轴输入具备基本稳定措施 | 通过 | 会话中性值、0.08 死区、灵敏度限制与一阶平滑均在 Provider 内。 |
| 推进符合边沿契约 | 通过 | B 长按只在进入 holding 状态时置一次 `boostPressed`。 |
| 系统返回约定未破坏 | 通过 | 现有 `KeyManager` 仍先检查 A+B holding。 |

### 构建验证与限制

- 输入源已重新配置进入 ESP-IDF 的构建规则，并完成 `esp-idf/main/libmain.a` 重新链接。
- `git diff --check` 通过。
- 本轮尝试完整镜像构建时，ESP-IDF 的组件管理器在离线检查和先前构建缓存切换后未能稳定完成重配置；这是本机构建环境状态，不是源文件编译诊断。提交前未将其描述为“完整固件构建通过”。
- 尚未刷机：IMU 轴向、灵敏度、B 长按手感、圆屏画面与帧时间都必须在真机上校准。
